## 启发式审计 vs. 实证审计

**本审计 = 启发式（heuristic）**。具体含义：

| 维度 | 启发式审计（本条目） | 实证审计（未做） |
|---|---|---|
| 数据来源 | 项目维护者记忆、checklist 状态、源代码印象 | 实际运行日志、用户访谈、A/B 测试、UX 录像 |
| "已具备"判定 | "我记得代码里有这功能" | 复现实验能跑通 |
| 时间投入 | 1-2 小时 | 数天到数周 |
| 可信度 | 中（启发式偏差不可避免） | 高 |
| 适合阶段 | 早期、需求不明、需要快速收敛 | 中后期、需要决策依据 |

**本审计明确承认的启发式偏差**：

- 维护者对自己维护的系统**过度乐观**：可能高估"已具备"项
- 容易把"工具层支持"误判为"UX 层完成"：例如 `vision_analyze` 工具存在 ≠ 用户能用拖拽图片输入
- 优先级判断受最近记忆影响：最近修复的 bug 容易被认为"还需要加强"
- 6 层模型中的"Emergence"层最容易被低估：因为它是涌现能力，不是显式功能

**修正偏差的机制**（建议在 v2 实施）：

1. 对每条 P0 / P1 项做"复现实验"：用一个真实任务走完该 UX 路径并截图
2. 对每条"已具备"项做"反例测试"：故意构造不满足该模式的场景，看是否真的失败
3. 邀请 1-2 个外部用户做 5 分钟走查，记录他们卡在哪里
4. 比对 4 周前后的同一类问题回复：是否有退化

## 审计方法

### 1. 起点

直接读取 `2026-06-26-hermes-agent-ui-shape-of-ai-checklist/notes.md` 中 7 类共 37 个模式的"自检问题 / Agent 场景 / 状态 / 优先级"四列。状态列已经是"启发式判断的最小单元"，审计在此之上做归类。

### 2. 归类

把 37 项按类别（7 类）+ 状态（已具备 / 部分具备 / 需改进 / 未评估）+ 优先级（P0 / P1 / P2）做交叉统计：

- 统计"已具备"比例反映**横向覆盖度**
- 统计 P0 数量反映**紧急程度**
- 归类"主要缺口"和"推荐改进"反映**可操作性**

### 3. 7 类各自的"当前判断 / 缺口 / 改进 / 优先级"4 列输出

每类一个 H3 章节，固定 4 段式结构（见 `notes.md`）。这样读者可以**跳读**而不会丢上下文。

### 4. P0/P1/P2 汇总

汇总表（notes.md 第二节）从两个角度排序：

- **按"对用户可见的破坏性"**（Stop / Source / Status 三态）排 P0
- **按"实施成本"**排 P1（不点名"代码量"，只点"复杂度"）

P2 不给细节，列名 + 一句话理由。

### 5. 第一轮建议

5 个主题：状态可见性、长任务进度、中断链路、动作区分、证据展示。每个主题对应 1 个 P0 行动项 + 1-2 个 P1 配套项。

### 6. 6 层映射

复用 checklist 的 6 层映射，**不重新做**。本审计在该映射上加入"覆盖度判断"列（覆盖度数字从 checklist 继承）。

### 7. 实施路线

按"先无代码 → 再报告 → 最后 UI"的顺序，理由是：

- **无代码阶段**最便宜：改 prompt / 话术 / 工具描述就能影响 UX
- **报告模板**次之：把"做了什么 / 证据"作为固定结构输出，能在不写 UI 的情况下满足 Source citation / Explanation 两个 P0 项
- **UI / Dashboard**最贵：按钮、组件、状态机都需要测试覆盖 + 跨平台适配

**反例**：如果一上来就做 UI 组件库，会遇到"需求还没收敛就先实现"的陷阱 — 当 P0 项的话术和模板已经够用时，UI 投入的边际效用很低。

## 维护约定

### 更新频率

- **v1（本条目）**：2026-06-26 初版
- **v2**：见 summary.md "何时做 v2" 章节的 4 个触发条件
- **不要做月度更新**：v1 → v2 之间不应有中间版本，避免审计口径漂移

### 与 checklist 的差异

| 维度 | checklist | 审计 (本条目) |
|---|---|---|
| 形式 | 37 个模式各 5 行 | 7 类 + P0/P1/P2 汇总 + 路线 |
| 时间 | 静态（"盘点现状"） | 动态（"建议改进 + 何时再做"） |
| 状态 | 模式级（每个模式一行） | 类别级（每类一个当前判断） |
| 优先级 | 模式级 P0/P1/P2 | 全局 P0 行动项 5 条 + P1 / P2 数量 |
| 输出 | 诊断 | 诊断 + 路线 + 实施建议 |
| 更新 | 月度 | 触发式（v1 → v2） |

### 与项目记忆的关联

本审计的"已具备"判断依赖的项目记忆：

- **MEDIA 协议**：Telegram / Slack 消息中可附带本地文件路径，自动上传为媒体
- **`/skill` 命令体系**：通过 `skill_view(name)` 加载 skill，引导 skill 行为
- **sub-agent 隔离**：`hermes-agent-spawning` / `delegate_task` / `ConPort` 提供独立 cwd 和工具集
- **session DB 持久化**：所有 session 持久化到 SQLite，可回看
- **Cronjob + Webhook** 异步触发：支持定时任务
- **多平台 home channel**：Telegram / Discord / 飞书 / iMessage 等可同时作为目标

如果项目记忆本身有误（例如某功能其实已下线），审计结论需要修正。这正是建议 v2 做"复现实验"的原因。

## 已知限制

1. **没有用户访谈**：所有"用户能否..."类判断都是维护者代理
2. **没有跨平台对比**：Telegram / Discord / Slack 的 UX 差异被合并
3. **没有量化指标**：覆盖度 49% / 22% 是相对数字，不是真实 KPI
4. **没有 A/B 实验**：所有改进建议都是单点
5. **审计者单一**：只有一个维护者视角，没有第二人 review
