## 2. Root cause

v0.3.19 (commit `787b4b8`) implemented the `initTrackPlayers` function in `site/app.js` to lazy-load YouTube embeds on the 10 verified tracks of the Paste 1960s listicle. However, the corresponding `TEMPLATE_FOOTER` in `scripts/generate_item_pages.py` did **not** include a `<script src="../../app.js">` reference, so `app.js` was never loaded on the 37 generated static detail pages.

Consequence: All 10 verified "▶ 播放" buttons rendered correctly but had **no click handler attached**. Clicking them was a no-op.

The bug was detected by the v0.3.21 batch-2 online smoke test (commit `2363a12`), which noticed 10 verified play buttons were present in the HTML but produced no iframe when clicked. The root cause was incorrectly attributed to wrong embed URLs at first; further investigation (and a successful local puppeteer test of the unmodified buttons) showed the actual root cause was missing JS loading.

Additionally, `app.js` was originally written for the home page only — it had top-level calls to `getElementById('search')` / `'records')` / `'stats')` / `loadData()` (which fetches `data/catalog.json`) that would throw on detail pages. Loading `app.js` on every detail page required guarding these home-page-specific paths.

## 9. Notes for future work

- `wrapper.innerHTML = ''` in `initTrackPlayers` causes a brief `Element.closest()` failure on the detached button if the handler re-queries `btn.closest('.track-actions')` after replacement. The current handler avoids this by capturing `wrapper` *before* `innerHTML = ''` and then calling `wrapper.appendChild(iframe)` using the captured reference. This is correct, but means the iframe insertion MUST happen before the wrapper is cleared — or the wrapper reference must be cached. The current code does the right thing.
- The duplicate-click test does not actually test the `btn.dataset.replaced === '1'` path because the button is fully removed from DOM after the first click (replaced by iframe). The dataset.replaced guard is therefore a defense-in-depth measure in case future code re-renders the button without re-binding click handlers. It is not strictly required for correctness given the wrapper replacement, but is kept for safety.
- The favicon.ico 404 console error is unrelated to this fix and predates v0.3.19. It is a GitHub Pages default behavior (no favicon.ico is shipped in the repo).
- Non-music item pages now also load `app.js`. This adds ~8KB to every detail page. Performance impact is negligible given the static nature of the site, but if size becomes a concern, a future optimization could load `app.js` only on pages that contain `.track-play-button` (detected by the JS itself).
