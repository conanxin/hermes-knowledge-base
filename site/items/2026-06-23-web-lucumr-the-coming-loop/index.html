The Coming Loop

_作者：Armin Ronacher，写于 2026 年 6 月 23 日_

"I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops."

—— Boris Cherny

我不再直接 prompt Claude 了。我跑的 loop 会去 prompt Claude，让它搞清楚要做什么。我的工作，是写 loop。

—— Boris Cherny

过去这几个月，我观察到越来越多人在 coding agent 之上搭出某种东西，感觉上和单纯"使用一个 coding agent"有着质的差别。其中一部分是建立在 Pi 之上的（看到这一点我挺高兴！），但各地的模式都一样：把工作放进某种队列，机器领走它、尝试、停下来，然后某个 harness 决定这是不是真的"结束"了。

如果没结束，harness 会延续同一个 session、注入另一条消息、带着改过的上下文开一个新 session，或者把任务派给另一台机器。任务会在模型自己通常会说"我做完了"那个点之后，依然活着。

我对这种 loop 想得比我想承认的还要多。

每个 coding agent 内部本来就有 agent loop。模型调一个 tool，吃下结果，再调另一个 tool，读一个文件，改一个文件，跑测试，最后产出某个答案。这种 loop，我们已经很熟悉很长一段时间了。另一种 loop 是 harness 层的 loop：agent loop 之外的 loop。这种 loop 也不新。自从 Claude Code 早期我们就一直在做各种版本，但最近几周它开始主宰 Twitter 上的话语。

我还不太擅长这件事

目前我的状态是：对于我在乎的代码——结果发现这种代码还挺多——我用这种方式做的成功率并不高。

一部分是品味，一部分是控制权。我给自己立的 bar 是很高的，我要理解我交付的代码。在压力下，或者和另一个人讨论时，我希望能在不先问一个 clanker（译者注：Armin 自创的俚语，用来指代 AI/机器人，含嘲讽亲切之意；字面是"嘎嘎作响的铁皮机器人"）解释的前提下，自己讲清楚系统做了什么。眼下还有一个问题：这种"要理解代码"的欲望，再过几年我还会不会有？目前我还没跨过"理解"对我来说仍然重要这道坎。

带着这个欲望，我缺一些东西——具体来说，是我对自己不仔细盯着的代码的体验，尤其当代码来自 loop 的时候。当下模型的产出倾向于过 defensive、过复杂、reasoning 过于局部。它们回避强不变量，用加 fallback 的方式替代"让坏状态根本不存在"。它们复制代码，编造糟糕的抽象，用更多 machinery 把设计模糊的地方糊过去。更糟的是：到目前为止我看不到这种状况有在改善的迹象。如果有的话，至少在这一点上，我感觉我们甚至在朝错误的方向走。起码按我的口味来说，今天像 Claude Code ultracode 那种 hands-off harness 产出的代码，比我们去年秋天产出的更差。原因在于：Claude Code（用 Fable 之类）会在一个问题上不停跑三十多分钟，而以前的过程是远更 human-in-the-loop 的。

而且广为人知的是，模型倾向于观察到某个局部失败就加一道局部防御。Karpathy 就提到过他们对 exception "怕得要死"。在有重要不变量的系统里——尤其是持久化的数据格式或核心基础设施——正确的修法不是"处理每一种畸形输入"。正确的修法是让畸形输入在类型上就不可表达，或在源头就不可能被写出来。然而即便有大量人工 steering，这类代码也不从 LLM 里自然流出；即便代码自然流出来了，它们仍然会试图处理那些已经不可能发生的错误。

当这种行为被塞到 loop 背后，问题会被放大。每一次迭代再加一道小防御，系统就会慢慢变得更难看懂，同时看起来更 robust。你越 hands-off，发生的就越多。而且当这种东西被交给 junior 而没有清晰指引时，会教出非常糟糕的实践——因为如果你问他们为什么那么做，他们会头头是道地说出道理。

Loop 适合的场景

与此同时，假装 loop 这种模式不工作也是不诚实的，因为在某些领域它已经工作得出奇地好。

代码移植就是其中之一。已经有不少大型自动移植工作让人印象深刻，包括报道过的把 Bun 从 Zig 移植到 Rust 的工作。我自己也成功用它把 MiniJinja 移植到 Go。性能探索是另一个它工作得很漂亮的场景：机器可以试实验、做 benchmark、丢弃失败结果、继续搜索。安全扫描天然合适，几乎任何类型的研究也都合适：让一个系统去探索一个复杂问题空间、再回来汇报，并不一定要提交持久的代码。这些场景的共同点是：它们要么不生成新代码、只是转换已有代码，要么生成的代码故意没有长的保质期。它们产出的是 proof-of-concept 或想法、是 surface findings，或者更接近一种机械转换。

我相信：那些产出不需要长寿 artifact 的 loop，或者做的是某种能被清晰验证的机械翻译的 loop，比那种"harness 能机械度量一个目标"的通用能力要重要得多。许多 loop 的成功应用会用另一个 LLM 作为 judge 或 orchestrator。机械翻译这种情况可以用二元的测试用例验证，但也可以用 LLM 来 judge！

比如 Claude Code 越来越擅长生成整个实验 workflow，然后再执行。它产出的代码确实是 slop，但这更多是模型的错，而不是 harness 不能判断一个 workflow 步骤是真正改善了还是完成了。

Harness 只需要某种信号让它继续。这个信号不必客观、不必二元，只要足够有用，能驱动下一次迭代就行。

我已经在用的、能把我一天里无聊的实验、测量、给我想法的那些 loop，我非常喜欢。

软件作为有机体

但反过来，用同一种 looping 方法论去写长寿的代码，我至今还是不太舒服。我喜欢用的一个隐喻是：从"软件是一台确定性机器"过渡到"软件是一个有机体"。

我成为一个软件工程师时，身处的环境鼓励我去理解那台机器。总是有一层你可以剥开来加深理解。行为不是确定性可观察的机器，不是完全不被接受，但一般被视为不算是最优的。在软件架构层面，我把它视为：要去推得更接近确定性而不是相反。同样的，"能看懂代码"一直是一个不可否认的目标。实际上这并不总是可能，但我们仍然以写出"即使新工程师也能通过巧妙架构去 navigate 复杂代码库"的代码为荣。在设计良好的系统里，总有工程师知道不变量住在哪、哪部分是 load-bearing、哪些改动是安全的。理想情况下这些也都文档化了。理解不到位的地方，一般被视为要去改进的东西。

显然这个理想一直是紧绷的。许多软件系统——尤其是很成功的那些——有过团队里有人能让代码保持整洁的阶段。大型软件系统常常太大、太动态、对外部服务依赖太多，不容易装进任何一个人脑子里。这是为什么长期以来工程师在分布式系统上的工作越来越像医生：我们观察症状，形成假设，"加测几条"，试几种治疗手段，再观察。

而有了 LLM，我们正在朝这个方向推得更远、也更快。我们让它们写代码，也让它们做诊断和开药方。已经有很多工程师活在这样一个世界里：生产出问题之后，第一步是让一个 clanker 读 log、提出根因、并主动提一个 patch。产出的 patch 经常又被另一台机器审了，有时甚至在完全没有任何人工监督的情况下直接落到 main。

显然这很强大，我也不能否认它听起来很吸引人。但接受这个想法——尤其当人工监督越来越少——意味着接受我们可能不再以同样方式理解整个系统了。我们治疗它、监控它、稳住它，但我们不一定懂它。

我毫不怀疑对某些软件来说这是 OK 的。并不是每一行代码都值得人工署名，而且过去写的代码里更糟的也有。

但我想不想让所有软件都以这种方式写出来？

你其实很难完全退出

非常不舒服的一点是：完全退出这个全机器驱动的未来，可能不是一个选项。

安全是最清晰的例子。今天，即便你不用 loop 来构建你的软件，别人会拿 loop 对你的软件做事。攻击者会持续跑机器，即便不是攻击者，安全研究者也会这么干，其中一些自动化工作会扬起尘土，但也会挖出真问题。信号和噪声会一起来、量大到几乎不可能处理，除非你自己也扔一台机器上去。

Daniel Stenberg 关于 curl 的「summer of bliss」的 post，是一个很好的关于维护者已经承受的压力的例子。据我所知，AI 今天在 curl 核心开发里还并不扮演巨大角色。但即便如此，维护者仍然被各种报告淹没，而其中多数都是 AI 生成的报告。

如果攻击者和报告者都 loop 了，防御者最终也得 loop 才能跟上。不一定是直接写 patch——可能只是 triage 和 reproduce——但压力会越来越大。

竞争上同样如此：有些团队会凭借原始速度构建得更快。有些项目会突然加速，因为一个小团队想明白了怎么 orchestrate 机器。有些初创公司会用 5 个人做到以前要 50 个人做的事。有些人可能会真的派一台机器去 loop 对着你的产品，让它"做得像那个对手"。如果他们的用户满意，这真的重要吗？

不是所有软件都会被同等影响。有些领域会惩罚粗糙、要求信任和责任；但大量软件活在一个原始速度、快速实验、广泛覆盖极其重要的世界里。

新的依赖

最让我害怕的是，我们会以新的方式依赖这些新机器。软件一直依赖工具。我记得有段时间我们要为编译器付钱。这些新工具像是一个 flashback：软件的创造再次带上真实成本。但这次不再是 one-time payment，而是一种持续依赖。不只是一个钱包被填满的依赖，也是一种认知上的依赖。

如果一个 codebase 是被 loop 产出、被 loop review、被 loop patch、被 loop 维持，当你不再能访问同一类系统时，会发生什么？如果某些贸易限制拿走了最强模型的访问权呢？如果只是成本变得不可承受呢？如果你和你的团队失去剩下那点"不靠机器也能理解代码"的能力呢？

我们可能会造出那样的 codebase：它们不仅对人类来说难以维护，而且维护模型本身就预设了机器参与。这件事已经在发生了！不是到处发生，也不一定以被看作问题的方式发生，但我们看到的越来越多。人们越来越多地合并他们无法完整解释的代码。人们越来越失去"不用 clanker 提供的上下文来增补或改写自己话"就写 issue 或在 chat 里讨论事情的能力。太多人在依赖一台机器来总结或 context 化对话。越来越多人在用 LLM 作 indirection 来和我对话。

再一次，也许这不是错的，但对我们做事方式而言是巨大的改变。

未来的 harness

我毫不怀疑这就是我们要去的地方，但要走到那里我们需要对所有 tooling 做些什么，而不仅仅是 coding agent。

仅仅 orchestrate 更多 loop 不够。更改动的可视化、或 orchestrator 的可视化、或 agent 的可视化，也不能恢复我们的理解。我们要不就是找到聪明的办法把人类重新 jolt 回 loop 里、让 loop 的改动长期可读；要不就是找到更好的办法来组合这些越来越复杂的系统。

这也是我对 Pi 角色的想法在变化的地方。Pi 一直很谨慎，我认为这种谨慎是好的。我不想要一个未来——每次交互都变成不可控的机器 swarm，做我看不懂的改动。我不想让 Pi 为了赢"软件自己写自己"这场赛跑而变成一个不可维护的烂摊子，也不想让 Pi 去 promote 这种工程方式。同时 Pi 又是一个 harness，而 harness 处在人们跑这些新实验的中心。

Coding 任务的任务队列、agent 的 orchestration、subagent、durable session，会越来越重要。即使是我们这些有保留意见、不盲信 loop 的人，也得开始做这些实验。我们必须做，因为我们必须理解如何让这个未来 bounded 且 survivable。

控制 loop

从这篇 post 你们也能看出，我对这种未来非常不安。不是因为恐惧，是因为基于截至目前的经验而产生的谨慎。

接受 harness loop 这个想法，意味着由 harness 来决定工作何时结束。在 agent loop 里，模型最终说"做完了"，我来 review。即便在之前，我通常也是中途在 steer。我参与其中，并享受沿途的学习。在 harness 跑的 loop 里，我不太确定我的角色是什么。甚至"做完了"这个信号也失去了所有意义，只是被传达给另一台做判断的机器。我的角色被简化成了一个 messenger。

今天我不怎么喜欢我看到的、由这种方式构建的系统产出的代码，我同样不怎么享受和"用 AI 协助构建出来的软件"互动。Looping 强大，但它越来越多地移除了责任，而且至少在今天，它非常鼓励我们向机器投降。

然而我毫不怀疑这个 looping 的未来就是我们的未来，尽管我现在对它心怀抵触。 我已经看到令人惊讶的小团队以不可思议的速度在 build，我看到 codebase 越来越变成只有更多机器才能诊断的、晦涩混乱的有机体。那些 codebase 同时是有用的和凌乱的。

所以我想我在接受：问题不是我们会不会 loop，因为显然我们会的。也许真正的问题是，在一个 loop 的未来里，我们如何不放弃判断（don't abdicate judgment），我们如何保留好的工程规则，我们如何确保负责任的人能继续 supervise，我们如何重新思考怎么架构代码，才能在这一路保持心智健全。
